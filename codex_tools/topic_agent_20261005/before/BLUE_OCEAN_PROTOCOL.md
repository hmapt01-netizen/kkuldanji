# 블루오션 발굴 공통 운영 기준

## 원문 열람은 리서치에서만 (2026-09-16 최종 사용자 지시)

이 절은 아래의 이전 단계 순서·본문 실사 요구보다 우선한다.
- 순서: 주제 후보·선택 → 네이버 제목·선택 → 구글 제목·선택 → 리서치 → 작성. 주제와 제목 단계에는 제목·검색 화면 요약만 본다. 기존 글 본문, 경쟁 글, 공식 원문을 절대 열람하지 않는다.
- 원문은 리서치 단계에서만 읽는다. 작성·이미지·검수 단계에는 리서치에서 작성한 source_notes.md와 자체 원고를 사용한다. 추가 원문이 필요하면 사유를 기록하고 리서치로 전환한 뒤 확인한다. 운영 규칙과 Python 소스의 유지보수는 콘텐츠 원문 열람에 해당하지 않는다.
- codex_tools/source_access_guard.py --work-dir 작업폴더 status로 상태를 확인한다. transition --phase titles --note 실제주제선택, 이후 transition --phase research --note 실제선택발언 --naver-title 확정제목 --google-title 확정제목으로 이동한다. 선택 발언을 만들지 않는다. 조사 완료 후 transition --phase writing --note 조사완료로 닫는다.
- 원문을 열기 직전에 이 도구의 check --resource URL또는경로를 실행한다. Python으로 읽을 때는 read --resource를 사용한다. 거절되면 브라우저·검색 도구·다른 명령으로 대신 열지 않는다. 웹 검색의 제목·요약 확인은 원문 열람과 구분한다.
- 도구는 단계와 허용·차단 내역을 source_access_state.json 및 source_access_log.jsonl에 기록한다. 연결된 read 실행은 리서치 외 단계에서 파일·네트워크 읽기 전에 차단한다. 도구 밖의 브라우저나 임의 명령을 OS 수준에서 감시하는 기능은 없으므로 에이전트도 반드시 사전 check를 지킨다.
- workflow_guard 제목 단계는 본문 실사·공식 출처를 선행 요구하지 않고 제목 형식을 검사한다. 경쟁 평가는 제목 기준 잠정 판단으로 표시한다. 이전 완료 기록은 새 순서에 맞춰 자동 조작하지 않는다. 기존 작업은 선택 발언과 산출물을 보존하고 새 순서로 재검증한다.


2026-09-14 사용자 지시로 개정. 꿀단지의 Codex·Antigravity·Gemini가 동일하게 적용한다.
주제·제목의 블루오션 판정은 이 문서가 AGENTS.md의 기존 자동 배지/성과 단정 예시보다 우선한다.
글쓰기 형식, 네이버/구글 제목 선택, 이미지 승인, Python 등록·검수·발행 절차는 유지한다.

## 최우선 목적

블루오션은 **검색하는 사람이 있는데 그 질문에 제대로 답하는 경쟁 문서가 부족하고,
꿀단지가 근거 있는 더 나은 답변을 제공할 수 있는 주제**다.
검색 수요 → 실제 경쟁 문서 → 답변의 빈틈을 먼저 검토한다.
신선한 소재, 공인 자료의 존재, 카테고리 균형, 광고 상품 연관성만으로 추천하지 않는다.
추천 전에 기존 본문의 검색 의도/결론 중복과 연결할 기존 글 2편도 검토한다.

## 수집과 판단 분리

1. `python tools/suggest_topics.py [시드]`로 기존 글 최신순/쿨타임, 자동완성, 뉴스 후보를 수집한다.
   출력 순서는 추천 순위가 아니다. 자동완성 0건은 검색량 0을 뜻하지 않는다.
2. `python tools/audit_serp_live.py naver "정확한 검색 질문" --review-template data/review_naver.json`
   또는 `google`로 채널별 검색 결과를 수집한다. 기존 인자 방식과 감사 JSON 파일명은 유지한다.
   광고/쇼핑/검색 내비게이션은 분리하고 중복 URL을 제거한다. 제목 링크로 식별된 일반 문서 최대 10개와
   전체 URL을 저장한다. 파서가 모든 화면을 인식한다고 가정하지 않는다.
3. **상위 일반 문서를 실제로 열어** `direct`(직접 답변), `partial`(일부 답변),
   `unrelated`(다른 질문)로 분류한다. `review_note`에 확인한 내용과 빠진 설명을 쓴다.
   제목의 단어 일치, 도메인 종류, 오래된 날짜만으로 이 분류를 자동 결정하지 않는다.
4. 차단·캡차·동의 화면·문서 0건·수집 실패는 블루오션 근거가 아니다.
   브라우저/허용된 검색 도구로 실제 결과를 확인하고 검토용 JSON에 원래 쿼리, 검색 URL,
   `collection_method: "browser"`, 실제 조회 시각, 실제 문서 목록을 기록한다.
   자동 수집이 실패했는데 화면도 보지 않고 `collection_status: "ok"`로 바꾸지 않는다.
   10개 미만이면 검색 범위와 실제 화면에서 확인한 부족 이유를 `coverage_note`에 쓴다.
   0개는 성공/빈집 판정으로 통과시키지 않고 추가 검색한다. 결과가 애매하면 검토 범위를 넓힌다.
5. 정확한 질문의 수요 자료와 답변 계획/공인 근거를 아래 스키마로 기록한다.
6. `python tools/audit_serp_live.py --import-review data/review_naver.json`으로 검토 기록을 검사한다.
   필수 근거 누락 시 종료 코드 1, 기존 감사 로그 유지. 성공해도 사실성이나 순위를 보증하지 않는다.
   `step_guard.py`는 구형 로그, 수집만 한 로그, 만료/미완료 근거를 다음 단계의 완료 증거로 허용하지 않는다.

## 기록 스키마 (감사 로그 schema_version=2)

`--review-template`은 수집 결과와 빈 검토란이 있는 사본을 생성한다. 기존 파일은 덮어쓰지 않는다.
네이버/구글은 별도 검토한다. 동일 제목 변형이 정확히 같은 쿼리/질문을 다루면 근거를 재사용할 수 있지만,
다른 질문이나 다른 채널의 조사 결과를 복제하지 않는다. 검토한 로그를 다시 수집하면 수집용 상태로 바뀌므로
작성 폴더에 검토 사본을 보존하고 필요할 때 검토 사본을 다시 import한다.

각 `records[]`의 필드:

- `clean_query`, `search_url`, `collected_at`(시간대 포함 ISO), `collection_method`, `collection_status`.
- `top_docs[]`: 실제 순서 `rank`, `title`, 원문 `url`, `answer_coverage`, `review_note`, `reviewed_at`.
- `coverage_note`: 10개 미만이면 실제 검색 범위와 부족 사유. 파서가 적게 찾았다는 것만으로 충분하지 않다.
- `review.query`: 해당 `clean_query`와 동일. `reader_question`: 해결할 실제 질문.
- `review.demand[]`: `kind`, `query`, `source_url`, `observed_at`, `period`, `value`, `interpretation`.
  - `kind`는 `search_volume`, `search_impressions`, `search_trend`, `repeated_questions` 중 하나.
  - 실제 수치 `value > 0`과 자료 기간/출처/조회일을 적는다. 구글 트렌드 상대 지수를 절대 검색량으로,
    광고 키워드 도구의 경쟁도를 일반 검색 경쟁도로 바꾸어 해석하지 않는다.
  - `query`는 실제 자료에서 확인된 질문과 일치해야 한다. 넓은 시드의 수치를 세부 질문의 값으로 옮기지 않는다.
  - `repeated_questions`는 같은 의도의 서로 다른 질문 원문 URL 최소 2개를 `question_urls`에 기록하고
    실제 개수를 value에 적는다. 이는 정성 수요 근거이며 월간 검색량 확인으로 보고하지 않는다.
  - 자료에 접근할 수 없으면 빈 배열로 남겨 추가 조사. 자동완성/AI 추정치를 채우지 않는다.
- `review.competition`: `high`, `medium`, `gap`; `competition_reason`: 상위 문서 근거에 따른 종합 판단.
  문서 수 고정 임계치나 사이트 규모만으로 자동 결정하지 않는다.
- `review.gap`: 해결되지 않은 구체적인 질문/조건. `answer_plan`: 우리가 더 제공할 정보와 구성.
- `review.sources[]`: `url`, `finding`, `checked_at`. 서로 독립적인 공인 근거 최소 2건.
  검사기는 서로 다른 호스트만 확인할 수 있다. 같은 연구의 재보도는 호스트가 달라도 독립 근거가 아니다.
- `review.duplication_review`: 관련 기존 본문을 읽은 결과, 차별화할 검색 의도와 연결할 슬러그/이유.
- `review.decision_reason`, `review.reviewed_at`: 최종 판단의 근거와 검토 시각.

검색/문서 검토는 24시간, 수요 자료와 공인 근거 조회 기록은 30일 내여야 한다.
조회일은 자료 발표일/측정 기간과 구별한다. 오래된 공인 연구를 오늘 발표된 자료로 쓰지 않는다.
기록 구조 검사는 실제 페이지를 읽었는지까지 증명하지 않는다. AI가 원문 대조 책임을 진다.

## 판정과 보고

- **💎 우선 공략 후보**: 해당 질문의 수요 증거 + 실사된 답변 빈틈 + 작성 가능한 근거가 모두 있음.
  블루오션 우선 조사/작성 대상으로 추천하되 순위·유입·수익을 보장하지 않는다.
- **🔴/🟡 보류**: 근거를 검토했지만 직접 경쟁이 높거나 중간이라 더 유리한 질문을 찾는 편이 나음.
- **⚠️ 추가 조사**: 수요/본문 실사/빈틈/작성 근거 중 하나라도 미확인. ‘수요 없음’이나 ‘블루오션’으로 둔갑 금지.
- 녹색 또는 임의 점수로 미확인 후보를 승격하지 않는다. 우선 공략 후보가 없으면 억지로 1~3픽을 채우지 않는다.
- 6대 사전 검토표와 SERP 표의 검토 항목은 유지하되 각각 확인/부분 확인/미확인을 정확히 표시한다.
  제목 10개 규격 통과와 블루오션 근거 완료는 다른 검사다. 수요/CPC/경쟁도를 제목 문법 점수로 대체하지 않는다.

## 발행 후 피드백

발행한 글의 동일 기간 검색어별 노출·클릭·평균 순위(자료에 있을 때)를 원래 후보의 예상과 비교해 기록한다.
색인 여부, 제목, 본문 충실도 문제와 주제 선택 문제를 나누어 판단한다.
접근 권한/실제 자료가 없으면 미확인으로 남긴다. 자동 모니터링이나 유료 서비스 가입은 이 문서로 승인되지 않는다.
## 주제 후보 선정 간소화 (2026-09-16 사용자 지시)

이 절은 주제 선택 전 상세 조사를 요구하는 이전 규칙보다 우선한다.

- 주제 선택 전에는 기존 글 제목과 검색 결과 제목만으로 우선 추린다. 화면에 보이는 요약·날짜는 보조 자료로 활용하며 본문을 열지 않는다. 저장된 조사 자료를 먼저 재사용한다.
- 후보 3개와 추천 1개를 먼저 제시하고 사용자의 주제 선택을 기다린다. 독자 질문, 제목상 중복 가능성, 추천 이유와 미확인 사항을 간단히 표시하고 탐색을 종료한다.
- 이 단계의 결과는 '블루오션 후보'다. 제목만으로 검색량·저경쟁·내용 중복 없음·답변 누락을 확정하지 않는다.
- 이 사전 후보 단계는 workflow_guard.py의 정식 research 완료와 구분한다. 후보 보고 전에 research 완료 검사·기록, 상세 근거 manifest, 본문 전수 검토, 공인 출처와 내부링크 확보를 요구하지 않는다. 상태가 research여도 주제 선택 전에는 상세 조사를 시작하지 않는다. 후보 요약·검색어·URL·확인일만 글별 작업 폴더에 저장한다.
- 주제 선택 후 선택된 주제만 정식 research와 기존 제목 선정 절차로 진행한다. 경쟁 글의 핵심 문단과 필요한 공식 자료를 확인하며 탈락 후보나 이미 확인한 자료를 반복 조사하지 않는다.
- 로그인 제한 자료는 본문 미확인으로 남기고 공개 자료를 활용한다. 후보 조사를 위해 로그인을 요청하지 않는다. 미확인을 실사 완료로 기록하지 않는다.
- 이후 사실 검증·제목 선택·이미지 승인·등록·발행 조건은 유지한다. 이전의 '제목 제시 전에 대기하지 않는다'는 지시는 사전 후보 3개를 제시한 뒤 주제 선택을 기다리는 경우에는 적용하지 않는다.
